一个实时界面偶尔晚几秒刷新，最容易得到的解释是“网络抖了一下”。但如果同一现象伴随着服务进程内存持续上涨、Swap 大量占用、重复日志突然放大，问题就不再只是网络延迟，而可能是一个完整的慢消费者失控链路：连接没有被正确回收，订阅回调不断累积，生产速度长期高于发送速度，历史消息最终把内存和进程一起拖垮。

这篇文章复盘一次典型的 WebSocket 慢消费者问题。重点不是某个项目的补丁，而是如何把零散现象组织成可验证的证据链，以及如何设计一个既理解消息语义、又能处理并发和背压的出站队列。

## 先定义问题：卡顿只是最外层症状

现场最直观的表现是：服务端状态已经切换，界面仍然显示旧状态，过一段时间才追上。与此同时还能观察到以下现象：

- WebSocket 服务进程内存接近所属 cgroup 的上限；
- 系统产生了远高于正常水平的 Swap；
- 进程曾被 OOM Killer 终止并重新拉起；
- 某类格式化错误在一秒内出现上千次，而正常状态源只有个位数赫兹；
- 重连后短期恢复，运行一段时间又逐渐变慢。

这些现象彼此相关，但仅凭其中任意一条都不能直接宣布根因。例如，高内存可能是缓存，也可能是泄漏；大量错误日志可能来自一个高频生产者，也可能来自同一消息被数百个回调重复处理。

因此，排查开始时先把结论分成三档：

| 证据等级 | 含义 | 示例 |
| --- | --- | --- |
| 直接证据 | 日志、指标或测试可以直接证明 | 进程占用约 1.8 GiB，cgroup 上限约 2 GiB |
| 高可信推断 | 现象与源码机制闭环，但缺少现场对象快照 | 失效订阅者造成回调扇出和对象长期存活 |
| 尚需验证 | 需要部署产物或持续压力测试确认 | 修复版本在长时间慢客户端场景下不再增长 |

这个分级很重要。事故分析的价值不在于把语气写得笃定，而在于让下一位排查者知道哪些结论可以复现、哪些仍需补证。

## 第一处陷阱：不要直接相减两台设备的时间戳

服务端日志和界面端日志通常来自不同设备。两台设备即使都显示“本地时间”，也可能存在秒级时钟偏差。如果直接用界面收到消息的时间减去服务端发布时间，会得到一个看似精确、实际并不可靠的端到端延迟。

更稳妥的方法，是在每台设备内部寻找同一状态变化的两个端点，再比较“变化过程持续了多久”。例如，经过脱敏后的样本可以写成：

| 观察位置 | 旧状态最后出现 | 新状态首次出现 | 本地间隔 |
| --- | ---: | ---: | ---: |
| 服务端状态通道 | T | T + 0.50 秒 | 约 0.50 秒 |
| 界面端 WebSocket | U | U + 2.75 秒 | 约 2.75 秒 |

这里不要求 `T` 等于 `U`。只要两台设备在短时间窗口内的时钟速率基本稳定，就可以确认：服务端半秒完成的状态切换，在界面侧被拉长到了约 2.75 秒，链路中额外出现了约 2.25 秒的排队或处理滞后。

还要确认比较的是同一通道。相邻时间出现的另一类错误消息，即使包含同名状态字段，也不能拿来替代状态通道的帧。通道混淆会把一条正确的时间线变成伪证据。

这一步只能证明“状态链路存在滞后”，不能独自说明滞后发生在序列化、WebSocket 发送队列、网络还是界面处理。下一步要寻找资源和调用次数的证据。

## 从内存、Swap 和 OOM 建立资源时间线

同一时间窗口内，WebSocket 服务进程占用了约 1.8 GiB 内存，而整个服务 cgroup 的限制约为 2 GiB。更早的系统日志还记录到：

- cgroup 的 RSS 触及限制；
- Swap 使用量达到十几 GiB；
- Python 进程随后被 OOM Killer 终止；
- 守护进程又把服务重新拉起。

这组信息比“进程内存很高”更完整。它说明问题已经从应用层积压扩散到系统层：大量仍被引用的 Python 对象无法释放，匿名内存被换出，访问旧对象需要触发换页，事件循环和消息处理延迟随之放大。最终，cgroup 内存上限触发强制回收，连接全部中断。

可以把退化过程概括为：

```text
消息生产持续快于网络发送
        ↓
待发送对象长期存活
        ↓
进程 RSS 增长，系统开始换页
        ↓
对象访问和事件循环变慢
        ↓
消费者更慢，队列积压进一步加剧
        ↓
触及 cgroup 上限并被 OOM Killer 终止
```

这是一条正反馈链。慢消费者不仅是结果，也会在 Swap 和调度压力出现后继续加重自身。

## 重复日志揭示了回调扇出，但不能当成订阅数

事故窗口中，一类相同的格式化错误在一秒内出现了超过一千次，而对应状态源的正常频率远低于这个数字。单个正常连接无法制造这种数量级，因此它强烈支持“同一输入被大量回调重复处理”的判断。

但不能简单地用：

```text
每秒错误条数 ÷ 状态发布频率
```

计算订阅者数量。原因包括：

- 一个源消息可能派生出多个通道；
- 同一连接可能订阅多个关联通道；
- 日志轮转可能只保留某个时间窗口的一部分；
- 格式化失败和正常发送未必是一一对应；
- 现场没有保存订阅注册表的对象快照。

因此，准确的表述是：重复日志证明存在严重的回调放大，失效订阅者是与源码机制一致的高可信解释；具体残留了多少订阅者，现有证据无法精确回答。

## 根因不是一个队列，而是三处缺陷互相放大

回到旧实现，可以看到三类问题叠加在一起。

### 1. 断连清理依赖了一次新的鉴权

连接建立时做身份校验是合理的，但旧代码在连接关闭时再次校验当前令牌。系统又只保存一个全局有效令牌；新登录会替换旧值。于是一个使用旧令牌建立的连接在关闭时可能走到这样的分支：

```python
def on_close():
    if not verify_current_token():
        return
    subscriber.disconnect()
```

关闭阶段的鉴权失败让 `disconnect()` 根本没有执行。连接在网络层已经消失，订阅注册表却仍持有订阅者；订阅者继续引用客户端对象，客户端又持有发送队列。

```text
订阅注册表
  └─ subscriber
       └─ client
            └─ sendq
                 └─ 历史消息及序列化结果
```

垃圾回收器无法回收这条仍可达的对象链。每次登录、重连和异常关闭都有机会再留下一个“僵尸订阅者”。

这里的设计原则很明确：**资源清理不能依赖一个可能失败、且与资源归属无关的业务校验**。连接既然进入了关闭流程，就应该幂等地释放它拥有的订阅和队列。

### 2. 订阅注册没有判重

如果同一个订阅者重复订阅相同或映射到同一底层源的通道，简单的列表追加会保留多个引用。之后每来一条状态消息，回调就会执行多次。

这既放大 CPU 和序列化开销，也让发送队列更快增长。正确做法至少要保证 `(底层通道, subscriber)` 在注册表中唯一；如果两个上层通道共享一个底层数据源，还要在映射后判重，而不是只比较用户提交的通道名。

### 3. 后台回调直接写入无界底层发送队列

旧路径中，缓存或消息总线的回调线程直接调用 WebSocket 的 `sendMessage()`。底层库会把帧追加到连接自己的发送队列，但没有按业务语义合并，也没有可靠的容量边界。

只要客户端读取速度低于生产速度：

```text
queue_growth_rate = producer_rate - consumer_rate
```

队列就会持续增长。更糟的是，状态消息的历史值通常没有发送价值：界面真正关心的是“现在是什么状态”，而不是在网络恢复后依次播放几分钟前的每一帧。

于是三处缺陷形成完整闭环：

```text
断连清理被跳过
        ↓
失效 subscriber 长期留在注册表
        ↓
重复注册进一步放大回调次数
        ↓
每个回调直接向无界 sendq 追加帧
        ↓
内存、Swap、CPU 和消息延迟共同恶化
```

## 修复目标：先定义消息语义，再谈队列

如果只给队列加一个最大长度，问题仍然没有真正解决：队列满时应该丢哪一条？丢弃确认消息可能破坏协议；保留所有状态历史又会重新制造延迟。

因此，修复先把出站消息分为两类。

| 类型 | 语义 | 拥塞策略 |
| --- | --- | --- |
| 状态类 | 新值覆盖旧值，消费者主要关心当前状态 | 每个通道只保留最新一条 |
| 事件、确认和错误类 | 每一条都可能有独立意义，通常要求顺序 | FIFO，不允许被同通道新消息覆盖 |

这里把“只保留最新状态”称为 QoS0，把可靠有序队列称为 QoS1。名称本身并不重要，重要的是分类必须来自业务语义，而不是消息大小或当前频率。

例如，位置、心跳、设备状态适合 latest-only；订阅确认、错误响应和必须按顺序处理的事件适合 FIFO。路线数据是否允许合并，则要依据上层协议决定，不能因为体积较大就擅自丢弃。

## 每个连接拥有独立 Outbox

修复后的数据路径不再让后台线程直接操作 WebSocket 库的发送队列：

```text
消息回调 / 请求处理
        │
        ▼
每连接 WsOutbox
  ├─ fifo: deque
  └─ latest: OrderedDict[channel, payload]
        │
        ▼
WebSocket 主线程 flush
        │
        ▼
底层 sendMessage / sendq
```

这个拆分解决了两个问题：

1. 后台生产者只负责 `push()`，不会跨线程修改底层 socket 状态；
2. Outbox 可以在进入底层发送队列之前应用消息合并和背压策略。

核心逻辑可以精简为：

```python
def push(channel, payload):
    with lock:
        if closed:
            return False
        if channel in latest_only_channels:
            latest[channel] = payload
        else:
            fifo.append(payload)
        return True
```

对状态通道连续写入十次，字典中仍只有一个槽位；最新值覆盖旧值。对事件通道连续写入十次，FIFO 中保留十条，等待按顺序发送。

### 配置文档和最终代码必须分别核对

早期方案曾计划用独立 JSON 文件维护 QoS 通道列表。但核对最终稳定代码后可以看到：当前实现把 latest-only 通道白名单定义为模块常量，运行配置只提供底层发送队列的软水位。

这类差异很常见，也是为什么事故文档不能只复述设计稿。上线审查应同时检查：

- 文档描述的目标行为；
- 稳定分支的最终文件；
- 实际部署包中的文件和校验值；
- 进程启动时真正加载的配置。

否则“修改配置即可生效”可能只是过期文档留下的错觉。

## 软水位不是 Outbox 的总容量

WebSocket 主线程每轮刷新时，先读取底层 `sendq` 的当前长度，再计算还能转移多少条消息：

```python
room = soft_limit - len(sendq)
if room <= 0:
    return 0

payloads = outbox.pop(room)
for payload in payloads:
    sendMessage(payload)
```

软水位的作用，是避免一次 flush 又把底层队列灌满。它限制的是“本轮可以从 Outbox 转移多少帧”，不是整个 Outbox 的硬上限。

弹出时先处理 FIFO，再处理各状态通道的最新值。这样可以优先保证 ACK、错误和事件消息的顺序，同时让状态数据在剩余空间中追到最新。

这种策略也留下了一个明确风险：如果 FIFO 持续高速写入，它可能长期占满每轮额度，导致状态消息饥饿。因此，软水位是背压机制的一部分，不是完整的流量治理方案。

## 订阅建立必须是一个临界区

订阅处理不只是“把对象加入列表”，通常还包含：

1. 读取当前状态快照；
2. 生成订阅 ACK；
3. 注册实时回调；
4. 把初始快照放入 Outbox。

如果这些步骤没有统一的同步边界，就可能在“读取快照”和“注册实时回调”之间漏掉一次更新。修复实现使用同一把可重入锁保护快照计算、ACK 入队、订阅注册和初始快照入队，让订阅者得到一个连续视图。

ACK 使用普通 FIFO 键，初始状态按通道进入对应队列。这样可以稳定保证：先收到订阅成功，再收到初始数据，而之后的实时更新不会从临界区缝隙中丢失。

注册表本身还要判重。共享同一底层源的两个上层状态通道，可以在生成输出时分别处理，但不应把同一个订阅者向底层列表追加两次。

## 断连顺序和迟到生产者

关闭连接时，正确顺序是：

```text
标记 subscriber 已断开
        ↓
关闭并清空 Outbox
        ↓
从所有订阅列表移除 subscriber
        ↓
清理客户端底层 sendq
```

`close()` 和 `push()` 使用同一把锁。这样并发结果只有两种：

- `push()` 先获得锁，消息进入队列，随后被 `close()` 清空；
- `close()` 先获得锁，后续 `push()` 看到 `closed=True` 并返回失败。

不会存在“队列清空后，迟到的后台回调又塞入一条永远无人消费的消息”。关闭操作也不再重新执行身份校验，确保清理路径与令牌状态解耦。

WebSocket 服务的主循环还需要隔离单连接故障：某个连接 flush 异常时，关闭并移除该连接，但继续处理其他连接。否则一个坏客户端可能阻塞整个服务循环。

## 如何验证修复，而不是只验证代码能运行

### 第一层：聚焦单元测试

本次核对中，生命周期和 Outbox 的聚焦测试共 17 项，全部通过。覆盖点包括：

- 非法软水位回退到默认值；
- 状态通道只保留最新值；
- 事件通道保持 FIFO 顺序；
- ACK 先于初始快照发送；
- 底层 `sendq` 达到软水位后暂停 flush；
- 后台线程只入 Outbox，只有主线程调用发送；
- 断连后拒绝迟到生产者；
- `close()` 与并发 `push()` 的顺序确定；
- 共享底层源的订阅注册保持唯一；
- 即使关闭时鉴权失败或鉴权函数异常，清理仍会执行。

单元测试证明了代码契约，但不能证明车辆或边缘设备正在运行这份代码。

### 第二层：部署产物验证

部署后至少确认：

1. 构建产物来自预期版本；
2. 关键文件的散列与审核版本一致；
3. 运行进程实际加载了这些文件，而不是旧的缓存或二进制扩展；
4. 启动配置中的软水位符合预期；
5. 不存在仍绕过 Outbox 的主要入口。

“代码已经合入稳定分支”和“现场已经运行修复版本”是两个不同结论。

### 第三层：持续慢消费者压力测试

构造一个主动降低读取速度的客户端，持续运行数小时，并反复执行连接、订阅、登录令牌更新和断连。测试期间观察：

- 活跃连接数和订阅者数量是否同步回落；
- 每连接 FIFO 长度、latest 通道数和底层 `sendq` 长度；
- 进程 RSS、Swap、GC 次数和事件循环延迟；
- 状态消息的新鲜度，而不只是发送吞吐量；
- stall 告警的连接、持续时间和恢复情况；
- 断连后是否仍有消息推向旧连接。

对状态通道，验收重点不是“每一帧都送达”，而是内存有界且客户端恢复后迅速看到最新状态。对事件通道，则要同时验证不丢失、顺序正确和过载策略可解释。

## 修复覆盖了什么，还没有覆盖什么

从最终代码和聚焦测试看，这套修改高可信地覆盖了本次事故的核心链路：

- 关闭连接无条件清理订阅者；
- 注册表避免同一订阅者重复加入；
- 后台线程与 WebSocket 主线程通过 Outbox 隔离；
- 高频状态不会在慢连接上保存无限历史；
- 底层发送队列有软水位；
- 断连后迟到消息会被拒绝；
- 生命周期和队列行为具备基础可观测日志。

但它不能被描述成“彻底解决所有 WebSocket 内存问题”。至少还有以下边界：

1. **FIFO 本身没有硬上限。** 如果可靠事件持续高于消费能力，Outbox 仍可能增长。
2. **FIFO 优先可能导致状态饥饿。** 需要按业务重要性增加配额、加权调度或最大等待时间。
3. **软水位按帧计数，不按字节计数。** 一条超大帧和一条小 ACK 被视为相同成本。
4. **慢连接只告警，不一定主动淘汰。** 长时间无进展的连接需要明确的断开策略。
5. **单一全局令牌仍会影响旧会话。** 清理已与鉴权解耦，但会话模型本身仍值得重新设计。
6. **旧协议入口可能绕过新 Outbox。** 所有入口都应做数据流审计，不能只验证主路径。
7. **应用层队列有界不代表内核缓冲和网络链路有界。** 仍需观测 socket 写入、系统发送缓冲和客户端处理时间。

## 一套可复用的排查顺序

遇到“WebSocket 偶发卡顿并伴随内存增长”时，可以按以下顺序推进：

1. 明确用户可见状态和对应消息通道，不混用相邻日志。
2. 校验设备时钟；有偏差时比较各设备内部的状态变化间隔。
3. 同时收集进程 RSS、cgroup 上限、Swap、OOM 和重启记录。
4. 统计消息源频率、回调执行次数和实际发送次数，寻找扇出放大。
5. 画出订阅注册表到客户端发送队列的对象引用链。
6. 审查所有关闭、异常、鉴权失败和重连路径是否都执行清理。
7. 检查注册是否幂等，尤其是多个上层通道共享底层源时。
8. 区分状态、事件、ACK 和错误消息的交付语义。
9. 检查队列是否同时具备数量、字节、时间和停滞边界。
10. 核对稳定分支、构建产物、现场文件和运行配置是否一致。
11. 用慢客户端、频繁重连和高频可靠事件做持续压力测试。
12. 分别记录已证实事实、机制推断和待验证风险。

## 结语

这次问题最值得复用的经验，不是“给 WebSocket 加一个队列”，而是三个更基础的原则。

第一，资源生命周期必须独立于可能失败的业务校验，关闭路径要幂等且必达。第二，背压策略必须理解消息语义：状态可以合并，事件不能被随意覆盖。第三，事故结论必须跨越代码、运行时和部署产物三条证据链；测试通过只证明代码契约，无法代替现场持续验证。

当系统能明确回答“谁在生产、谁在消费、积压存在哪里、满了以后牺牲什么、连接关闭后谁负责回收”，慢消费者才从一个偶发故障，变成一个可以设计、测试和监控的正常工程场景。
