## 摘要

一个运行在 Kubernetes 中的 go-zero 服务偶发 Redis 慢调用：普通 GET、SET 等小数据量操作的客户端耗时会突然升到约 160ms，并以数秒到数十秒的间隔反复出现。

排查过程中，Redis 服务端、网络、连接池和 Go 调度器都出现过值得怀疑的信号。但把不同 Pod 的累计指标或不同时刻的慢日志直接拼在一起，很容易得到错误结论。最终能够稳定解释现象的关键，是容器获得了 1.5 核 CPU 配额，而进程实际的 `GOMAXPROCS` 只有 1。go-zero 使用的自动适配逻辑会将小数 CPU quota 向下取整，因此 1.5 核被转换成了 1 个 Go 逻辑处理器。在高并发场景下，这会让客户端请求处理、序列化、连接池管理和响应回调共享单个可执行 Go 代码的逻辑处理器，从而放大排队时间和尾延迟。

灰度将 `GOMAXPROCS` 调整为 2 后，慢调用明显改善。这说明并行度不足是本次问题的重要原因。不过，Redis 服务端确实出现过慢命令和延迟尖峰，连接池也出现过空闲连接耗尽，因此更准确的结论不是“Redis 完全没有问题”，而是：**客户端并行度不足构成了可复现、可干预的主要放大因素；服务端与连接池仍需通过同 Pod、同时间窗的证据继续观察。**

长期方案是升级到 Go 1.25，并采用其原生的容器感知 `GOMAXPROCS` 默认行为。Go 1.25 会在 Linux 上读取 cgroup CPU limit，对 1.5 这类小数配额向上取整，并在配额变化后定期更新运行时并行度。

## 一、问题现象

服务运行环境的关键条件如下：

| 项目 | 观测值 |
| --- | --- |
| Go 版本 | 1.23.x |
| 部署方式 | Kubernetes，多副本 |
| 单 Pod CPU limit | 1.5 核 |
| Redis 最大连接数 | 约 180 |
| 并发业务规模 | 百级长连接设备 |
| 慢调用表现 | 普通 Redis 操作偶发约 160ms |
| 慢调用间隔 | 约 5～20 秒 |

这里的“Redis 慢调用”最初来自客户端侧耗时统计。它表示从业务代码发起调用到收到结果的整段时间变长，但不能直接证明这段时间全部消耗在 Redis 服务端。完整耗时至少可能包含：

1. 请求 goroutine 等待被 Go 调度器执行；
2. 从连接池获取连接；
3. 网络发送与排队；
4. Redis 执行命令；
5. 网络返回；
6. 客户端 goroutine 再次获得调度并处理响应。

因此，第一步不是立即扩大连接池或归因网络，而是把这些边界分别验证。

## 二、排查过程

### 1. 连接池确实可疑，但最初的指标不能直接定因

通过服务的 Metrics 接口检查连接池时，曾看到空闲连接数降到 0，累计获取连接超时次数也比较高。这个现象说明请求可能等待连接，连接池方向值得继续排查。

但当时的采样通过 Kubernetes Service 完成。多次请求可能分别落到不同 Pod，而连接池的 `hit`、`miss`、`timeout` 等又是各进程独立累计的计数器。如果把不同 Pod 的两次结果相减，会制造出并不存在的突增或回落。

所以这组证据只能支持：

- 至少有实例出现过连接池压力；
- 连接池等待可能贡献部分客户端耗时；
- 需要固定 Pod 后重新采样，并使用时间序列增量比较。

它不能单独证明每一次约 160ms 的慢调用都是连接池耗尽导致的。

### 2. Redis 服务端出现过尖峰，但缺少逐次时间关联

Redis `SLOWLOG` 和延迟探测曾记录到以下现象：

- 普通 GET 的服务端执行耗时曾达到约 40ms；
- 一次包含大参数的 LPUSH 耗时约 80ms；
- 延迟探测的最大值曾接近 100ms。

这些数据证明 Redis 并非始终处于低延迟状态，大对象写入、瞬时负载或服务端调度都有可能造成尖峰。但它们仍不能直接解释所有客户端慢调用：

- `SLOWLOG` 只记录 Redis 内部执行时间，不包含连接池等待和网络往返；
- 观测到的慢命令不一定与业务日志中的慢调用发生在同一秒；
- 某个 Pod 的网络探测正常，只能降低普遍性网络故障的可能，不能排除单实例或瞬时抖动。

要建立因果关系，需要给客户端慢调用、连接池等待和 Redis 命令附加可关联的时间戳，最好还能关联请求 ID，再按同一事件逐条对齐。

### 3. `Cpus_allowed_list` 不等于容器拥有的 CPU 配额

容器内的 `/proc` 信息显示进程可以在宿主机很多逻辑 CPU 上运行。这个结果一度让人误以为容器能够使用很多核。

实际上，需要区分两种约束：

- CPU affinity 或 `Cpus_allowed_list` 决定进程可以在哪些逻辑 CPU 上运行；
- cgroup CPU quota 决定进程在一个调度周期内最多可以消耗多少 CPU 时间。

本例 cgroup v1 中 quota 为 150000、period 为 100000，所以平均 CPU 吞吐上限是 1.5 核。即使 affinity 允许进程在几十个逻辑 CPU 之间迁移，它在每个周期内仍然只能消费相当于 1.5 核的 CPU 时间。

### 4. 运行时指标暴露了真正的配置错配

服务运行时指标显示：

```text
go_goroutines 4000+
go_sched_gomaxprocs_threads 1
```

goroutine 数量会随业务负载变化，单次采样不能代表稳定值；但 `go_sched_gomaxprocs_threads 1` 明确表示 Go 运行时只有一个 P，也就是同一时刻最多只有一个执行上下文可以运行 Go 代码。

这并不意味着整个进程只能创建一个线程，也不意味着网络 I/O 会始终阻塞。处于系统调用中的线程不受同一种限制，goroutine 也可以非常多。但当大量 goroutine 同时变为 runnable 时，它们必须竞争唯一的 P。业务逻辑、编解码、日志、Redis 客户端回调以及运行时工作都会在这个执行槽位上排队。

对以 I/O 为主的服务，`GOMAXPROCS=1` 不一定立即造成平均延迟恶化，因为 goroutine 在等待网络时会让出执行权。问题往往出现在负载尖峰、批量消息、垃圾回收或大量响应同时返回时：短时间内 runnable goroutine 增多，单 P 排队首先体现在 P95、P99 等尾延迟，而不是稳定复现于每一个请求。

### 5. 为什么 1.5 核最终得到 `GOMAXPROCS=1`

不能简单地说“Go 1.23 默认把 `GOMAXPROCS` 设为 1”。Go 1.24 及更早版本的原生默认值主要来自启动时可见的逻辑 CPU 数量，并不会原生读取 Kubernetes CPU limit。

本例所用的 go-zero 版本包含一层容器适配：框架初始化时调用 `go.uber.org/automaxprocs`，根据 cgroup CPU quota 设置 `GOMAXPROCS`。该依赖的默认换算函数对小数 quota 向下取整，最小值为 1。因此：

```text
CPU quota / period = 150000 / 100000 = 1.5
floor(1.5) = 1
GOMAXPROCS = 1
```

这解释了为什么宿主机有很多逻辑 CPU、容器 limit 为 1.5 核，而 Go 运行时指标仍然是 1。

镜像构建文件里虽然曾写过 `ENV GOMAXPROCS=5`，但它位于 builder 阶段。多阶段构建中，每一个 `FROM` 都会开启新的镜像阶段；builder 阶段的环境变量不会自动进入最终运行阶段。因此，源码仓库“写过配置”不等于生产进程“实际获得配置”。运行时 Metrics 才是最终证据。

## 三、原因判断

这次问题可以分成三层。

### 直接机制：运行时并行度低于可用配额

容器可以获得 1.5 核 CPU 时间，但 `GOMAXPROCS=1` 让 Go 代码最多只使用一个并行执行槽位。在并发请求较多时，额外的 0.5 核配额无法被同一时刻运行的 Go 代码充分利用，runnable goroutine 更容易形成队列。

Redis 客户端耗时覆盖了调用前后的 Go 调度时间，因此即使 Redis 命令本身执行很快，客户端仍可能记录到百毫秒级长尾。

### 配置原因：小数 CPU quota 被向下取整

框架使用的自动适配库把 1.5 向下取整为 1。这个策略可以减少进程超过配额后遭遇 CFS throttling 的风险，但也会放弃小数配额中的剩余吞吐能力。对 CPU 较慢、goroutine 数量较多或突发负载明显的环境，这种差异更容易暴露为排队延迟。

### 放大条件：服务端尖峰与连接池压力

Redis 曾出现慢命令，连接池也曾出现空闲连接耗尽。它们可能与单 P 调度共同放大尾延迟，但由于早期证据没有固定到同一个 Pod、同一时间窗和同一次请求，不能把三者拼成已经证实的单一因果链。

因此，本文将根因边界表述为：

> 已确认的主要问题是容器 CPU limit 与 Go 运行时并行度不匹配；它造成客户端调度排队，并放大 Redis 调用的长尾。Redis 服务端尖峰和连接池等待是同时存在的风险因素，但对每一次慢调用的贡献比例仍需关联数据验证。

## 四、为什么调整为 2 后能够改善

灰度把 `GOMAXPROCS` 从 1 调整为 2 后，Redis 慢调用频率明显下降。这个 A/B 结果与调度机制相符：

- 两个 P 可以同时执行两条 Go 代码路径；
- 当多个网络响应同时返回时，回调和后续业务处理不再全部串行；
- Redis 连接池的管理、日志和业务 goroutine 不必始终竞争唯一的 P；
- 进程能够利用 1.5 核 quota 中原先闲置的部分吞吐能力。

但 `GOMAXPROCS=2` 高于 1.5 核平均吞吐上限，理论上也可能增加 CPU throttling。它不是一个只看延迟、不看代价的固定答案。灰度期间需要同时观察：

- Redis 客户端延迟的 P50、P95、P99；
- `container_cpu_cfs_throttled_seconds_total` 等 throttling 指标；
- Pod CPU 使用率；
- Go 调度器 runnable 队列或运行时 trace；
- 连接池等待时间、空闲连接和获取超时增量。

如果尾延迟下降而 throttling 没有显著恶化，设置 2 才能算适合当前负载。

## 五、长期方案：升级到 Go 1.25

Go 1.25 原生引入了容器感知的 `GOMAXPROCS` 默认行为。在 Linux 上，运行时会综合考虑：

1. 机器的逻辑 CPU 数量；
2. 进程 CPU affinity 可用数量；
3. cgroup CPU throughput limit。

对于 1.5 核 CPU limit，Go 1.25 会把小数配额向上取整，而不是像本例使用的旧适配逻辑那样向下取整；在逻辑 CPU 和 affinity 允许的情况下，默认结果会是 2。运行时还会定期检查 CPU affinity 和 cgroup limit 的变化，动态更新默认并行度。

这正好覆盖了本次问题中的两个薄弱点：

- 不再需要依赖应用框架额外注入一次性的容器适配逻辑；
- 小数 CPU limit 不会因向下取整而损失可用并行度。

不过，“升级编译器”并不自动等于“新默认已经生效”。Go 的兼容机制可能依据 `go.mod` 中的 Go 语言版本选择旧的 `GODEBUG` 默认值。落地时应同时确认：

- 构建工具链确实为 Go 1.25 或更高版本；
- `go.mod` 的 `go` 指令已经升级到 1.25 或更高版本；
- 没有显式设置 `GOMAXPROCS` 环境变量；
- 代码或依赖没有再次调用 `runtime.GOMAXPROCS` 覆盖默认值；
- 没有设置 `GODEBUG=containermaxprocs=0` 或 `updatemaxprocs=0`；
- 启动后 Metrics 中的 `/sched/gomaxprocs:threads` 符合预期。

Go 1.25 的行为可参考 [Go 1.25 Release Notes](https://go.dev/doc/go1.25#container-aware-gomaxprocs) 和 [Container-aware GOMAXPROCS](https://go.dev/blog/container-aware-gomaxprocs)。go-zero 的初始化逻辑与旧适配库的取整策略可分别参考 [go-zero `core/sysx/automaxprocs.go`](https://github.com/zeromicro/go-zero/blob/master/core/sysx/automaxprocs.go) 与 [`automaxprocs` CPU quota 转换实现](https://github.com/uber-go/automaxprocs/blob/v1.6.0/internal/runtime/cpu_quota_linux.go)。

## 六、推荐的升级与验证步骤

### 阶段 1：建立升级前基线

固定一个 Pod，连续记录以下数据，避免再通过 Service 随机采样不同实例：

- 当前 Go 构建版本和 `go.mod` 版本；
- `GOMAXPROCS`、goroutine 数量和 CPU 使用率；
- Redis 客户端 P50、P95、P99；
- 连接池当前连接、空闲连接、等待次数和超时增量；
- Redis `SLOWLOG` 与服务端延迟；
- cgroup throttling 时间和次数。

### 阶段 2：在同等资源下升级

保持 Pod CPU request、limit、副本数和业务流量策略不变，只升级 Go 工具链及 `go.mod`，并清理旧的显式 `GOMAXPROCS` 覆盖。这样才能把差异尽量归因于运行时行为变化。

### 阶段 3：验证实际运行值

启动后不要只查看 Dockerfile 或镜像标签，应从进程 Metrics、启动日志或 `runtime.GOMAXPROCS(0)` 确认运行值。对于 1.5 核 limit，预期值是 2；如果仍为 1，需要继续排查环境变量、框架初始化和 `GODEBUG`。

### 阶段 4：灰度比较尾延迟与 throttling

在相同业务时段比较升级前后数据。验收标准不应只有“没有再看到一条慢日志”，而应至少包括：

- Redis 客户端 P95/P99 持续下降；
- 慢调用频率下降；
- CPU 使用更加接近但不长期顶满 limit；
- throttling 没有出现不可接受的增长；
- 连接池超时增量不再持续升高；
- Redis 服务端慢命令能与剩余客户端慢调用逐次关联。

## 七、结论

本次 Redis 长尾延迟不是单看一条 `SLOWLOG` 就能解释的问题。排查的关键，是把 Redis 服务端执行时间、连接池等待、网络往返和 Go 调度时间拆开，并确保所有指标来自同一个 Pod、同一个时间窗。

最终确认的主要矛盾是：Pod 拥有 1.5 核 CPU limit，但旧的容器适配逻辑将小数 quota 向下取整，使进程运行在 `GOMAXPROCS=1`。在大量 goroutine 和突发并发下，单 P 调度放大了客户端侧的排队与尾延迟。灰度调整为 2 后现象改善，为这一判断提供了直接的运行结果支持。

短期可以显式设置与资源配额相匹配的 `GOMAXPROCS` 并持续观察 throttling；长期更推荐升级到 Go 1.25，使用运行时原生的容器感知能力。升级时必须同步更新 `go.mod`，移除冲突的手工覆盖，并通过运行时指标验证新默认确实生效。

更普遍的经验是：**资源配置、框架自适配和程序运行时是三个不同的事实层。Dockerfile 写了什么、Kubernetes 分配了什么，都不能替代对进程实际状态的验证。**
