## Where the problem starts

When an application observes a disconnected connection, calling `socket.close()` only releases local connection resources. Recovery also depends on whether a new connection can be established, subscriptions become active again, and messages are handled while the connection is down.

## A minimal experiment

Run a Broker and two test clients locally, then publish numbered synthetic messages at a fixed interval. At minimum, record:

1. Connection state and reconnection time before and after the disconnect.
2. Whether subscriptions recover as expected.
3. Whether message sequence numbers contain gaps or duplicates.
4. Differences across QoS and session configurations.

```text
publisher → test broker → subscriber
                 ↓
           disconnect / reconnect
```

## Boundaries to make explicit

Use backoff and jitter in the reconnection loop so many clients do not retry together. Validate subscription recovery, idempotent handling, and persistent sessions against the selected client library and Broker configuration. One successful reconnect is not evidence that the link is reliable.
